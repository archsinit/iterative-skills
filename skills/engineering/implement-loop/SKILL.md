# Implement Loop

Run `/grill-the-basics` then `/to-spec` first. Read the persisted spec, applicable host/project instructions, relevant code/docs and the latest iteration evidence. If the handoff is missing, ask the human to run `/to-spec`; do not substitute a ticket tree or infer permission. This skill is instructions inside an active session, NOT a scheduler or perpetual wake engine. Add no scheduler or dependencies merely to keep running.

## Establish the envelope

Before writes or runtime actions, confirm the spec's authorised scope and local-commit permission in this host environment. Higher-level restrictions always win. Require a finite approved overall slice count and elapsed run-time limit before autonomous multi-slice execution; without them, stop for approval. Each candidate gets one initial implementation/verification pass and at most TWO focused repair rounds, or the lower approved cap. Track total elapsed time, slices and repairs in durable iteration records. Resume uses the same remaining budget, not fresh counters. Subagents, splitting or relabelling the same candidate cannot reset it.

Pin the starting checkpoint SHA for this authorised run (or explicitly record no verified starting checkpoint and pin the initial commit baseline). Keep that fixed reference through all slices for the final cumulative review.

Inspect Git state. Preserve dirty/unrelated work; never reset, clean, stash others' work, auto-checkout over changes, amend someone else's commit or stage everything indiscriminately. Work on the authorised branch or create a new candidate branch/worktree if permitted. No automatic publication, push, external communication, spending, destructive action or production migration. Those require separate authority even if another skill suggests them.

## Preserve a runnable checkpoint

Before evolving a candidate, identify the latest genuinely verified runnable commit (or state explicitly that none exists). Preserve its history and a practical inspection path. Read [CHECKPOINTS.md](CHECKPOINTS.md) for a portable worktree mechanism and runtime/data safety. Keep the last-good surface available while the candidate changes. A passing unit suite alone is not a runnable checkpoint. Never replace last-good with a failed or untried candidate.

## Iterate inside the mandate

1. Select the next numbered smallest end-to-end slice from the spec's outcomes. Refine its acceptance/failure expectations precisely; later slices stay provisional. Choose reversible technical means yourself. Explicitly flag changes to accepted behavior and stop unless already authorised. Do not require human inspection or approval per slice inside an approved multi-slice envelope.
2. Build the slice through its real user surface, not just scaffolding. Prefer existing tests/tooling and no speculative abstractions. Tests must trace to approved outcomes, accepted guarantees or concrete relevant risks; they cannot invent requirements. Choose proportionate test seams yourself. Call the Skill tool with "tdd" where useful; its fork-compatible discipline chooses technical seams within authorised outcomes, asking only for material decisions.
3. Verify the actual surface (browser interaction, CLI invocation, API request or other real entry point), relevant failure handling and regression risks. Record commands, outcomes and safe evidence references. Do not claim unavailable checks ran or claim output usefulness solely from green tests.
4. Review EVERY current slice against both the spec and coding standards, alongside actual runtime verification, BEFORE a commit can be labelled a runnable/working checkpoint. These reviews are built into the loop; the human need not invoke `/code-review` to trigger them. Use proportionate independent review for consequential changes where tools/permissions allow: give the reviewer the spec, fixed baseline, diff including relevant uncommitted/new files, actual-surface evidence and a narrow request to challenge correctness, scope, failure paths, safety and accepted behavior. Use isolated workers only if permitted; no recursive or unbounded delegation. If independent review is unavailable, label the review SELF-REVIEW and perform those checks yourself. Assess each finding against intent/evidence; fix relevant defects, explain rejected findings, do not blindly apply every suggestion. Call the Skill tool with "code-review" where useful for separate Standards and Spec axes. Its fork-compatible workflow reads the local versioned spec first and includes relevant staged, unstaged and new files for the current slice; it uses permitted background reviewers or labels self-review. Do not reintroduce tracker prerequisites, recursive delegation or human seam gates.
5. On a concrete failure, spend at most the remaining repair rounds. Each round records observed failure, contract relevance, new hypothesis/fix and retest evidence. After any post-review change, perform proportionate Standards and Spec review of the resulting repaired diff and rerun affected actual-surface and regression checks BEFORE runnable promotion. Review evidence from a pre-repair state cannot certify the repaired state; trivial changes need not repeat a full independent review. These checks consume the existing remaining budgets. If required evidence is unavailable or the budget expires, label the candidate NOT runnable. Stop early on repeated failure without new evidence, expanding scope, broken regressions, or an unapproved decision. Never weaken approved acceptance checks just to pass; explain correction of mistaken implementation tests.
6. At the end of the authorised run, perform a cumulative Standards and Spec review from the fixed STARTING checkpoint/baseline through all slices and relevant current uncommitted/new files. Check integration, cross-slice drift, accepted behavior and combined runtime evidence, not just the last diff. Do this before the final checkpoint commit when the ending is known. If an unexpected stop happens after a commit, record the cumulative assessment in a scoped evidence commit when authorised; do not claim an unavailable review passed. Any resulting repairs consume the same remaining candidate AND overall budgets; do not reopen an exhausted run. Apply the same post-repair Standards/Spec review and affected runtime/regression rechecks to cumulative-review fixes before runnable promotion.

   End EVERY iteration with a scoped local commit, only with valid host authorisation. Include code, relevant spec changes and a concise tracked record such as `specs/<outcome>/iterations/001.md`: slice/candidate, baseline and last-good references, approval/budget consumed and remaining, verification passed/failed/unavailable, per-slice Standards/Spec review mode/findings/disposition, final cumulative review status from the starting checkpoint when ending the run, assumptions, acceptance status, how to try, and next action. Inspect the staged diff; exclude secrets, private runtime data and unrelated files. A blocked write with no code change can commit just its safe evidence record. If committing is forbidden or fails, stop and report; never claim a commit exists.
7. Label verified commits `runnable checkpoint: slice N ...`; label failed/incomplete commits `NOT runnable: slice N ...`. Record status in the repo too. Promote last-good only after all required verification passes. Human acceptance remains separate: technically verified is READY FOR HUMAN TRIAL, not accepted. Human silence is not acceptance.
8. Continue to the next slice WITHOUT mandatory per-slice approval when inside the approved envelope. The human may inspect, redirect or pause at any point. Stop when the outcome is achieved, time/slice/repair budget is exhausted, a genuine blocker arises or a product/permission decision exceeds the mandate. Leave evidence and the latest runnable checkpoint usable; no automatic retries after the stopping limit.

Report what works, how to try, evidence, review mode, commit/status, remaining uncertainty and budget, and whether a human decision is needed. The human may run `/code-review` for further scrutiny and then optional `/retro` for environment learning; neither is a mandatory gate or permission to expand access. Failure is a useful result when diagnosed honestly.

## Branch and resume

When the human chooses an earlier checkpoint, verify its SHA and clean state, then create a NEW branch from it (prefer a new worktree); preserve the original branch/history. Never destructive reset or automatic checkout over dirty work. Specs travel with code. Ask the human to rerun `/grill-the-basics`, then `/to-spec`, then `/implement-loop` on the new branch, capturing the redirected intent, accepted-behavior changes and a newly explicit envelope rather than silently reusing stale authority.
